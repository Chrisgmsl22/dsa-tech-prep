Strategy
One job, several rules.

Strategy separates a task from the rule that performs it. You can replace the rule through the same contract.

Use this guide to explain the pattern, then design your own small price-rule exercise.

The idea How it works Python refresher Your first attempt
01 / The idea

The job stays the same. The rule varies.

A coffee shop needs a final price. The shop can apply full price, a happy-hour rule, or a staff discount.

All three rules answer the same question. Each rule can calculate its answer in a different way.

Strategy puts each variation behind a shared contract: the operation, accepted inputs, expected result, and behavior that callers can rely on.

The caller uses that contract. It does not need the details of each calculation.

Picture a cashier with a policy card. The cashier asks for the final price through the same request each time.

A different card changes the price rule. It does not change the cashier’s task.

02 / The mechanism

One object delegates work to another.

Delegation means that one object asks another object to perform part of its work.

RoleResponsibility
ContextUses a strategy to complete part of its task.
Strategy contractDefines what all interchangeable strategies must support.
Concrete strategySupplies one version of the rule.
ClientChooses a strategy and supplies it to the context.

The client supplies the choice. The context calls the selected strategy. That strategy returns the result.

The choice still exists. Strategy moves it away from the code that uses the rule.

You can select a strategy when you create the context. A later replacement is optional.

03 / The trade-off

Separate a real variation.

  • Strategy helps when alternative rules change independently.
  • Extra classes cost effort when a small, stable conditional already expresses the task clearly.
  • Python functions can serve as strategies. The pattern does not require a class for every rule.

For this exercise, use objects to practise a shared contract. Your existing stub points toward an abstract base class.

04 / Python refresher

Use these concepts to express the design.

Consult the terms you need within the same ten-minute read. You do not need a separate prerequisite exercise.

ConceptQuick reminder
Class and instanceA class defines a type. An instance is one object of that type. Define a class with class.
Function and methodDefine a function with def. An instance method operates on an object. Its first parameter conventionally has the name self.
Parameters and argumentsA parameter names an input in a definition. An argument supplies a value in a call.
selfRefers to the current instance. A method call through an instance supplies that instance automatically.
__init__Initializes an instance after Python creates it. It establishes the data and collaborators that the object needs.
Instance attributesHold data for a particular object. A mutable class attribute can share data across instances by accident.
Return valuereturn gives a result to the caller. A function without an explicit result returns None. A print only produces output.
CompositionAn object holds another object as a collaborator. The context uses the rule through that object.
InheritanceA subclass derives from a base class. It can supply its own implementation of a method.
PolymorphismDifferent objects support the same operation. The caller uses that operation without a separate branch for each concrete type.
Type hintsDescribe expected types for readers and type checkers. Python does not enforce ordinary type hints at runtime.

Python references: classes and methods, functions, and type hints.

An interface describes a promise.

Python has no dedicated interface keyword. You can express a shared contract in several ways.

  • Duck typing: the caller uses the required operation. The object must support it.
  • Abstract base class: ABC supplies an explicit base type. abstractmethod marks a method that a concrete subclass must implement.
  • Protocol: describes the required members for structural type checks. A class with those members need not inherit from it.

Python prevents direct instances of an abstract class while abstract methods remain unresolved. It does not prove correct method signatures or behavior.

05 / If you get stuck

Check the contract before you add more classes.

SymptomFirst check
Every new rule changes the caller.Does the caller use a shared operation, or inspect concrete types?
A replacement rule breaks the result.Do the rules agree on input units, output type, and output meaning?
Python refuses to create an object.Does that class still have an abstract method without a concrete implementation?
